# 项目编码规范

## 测试用例设计与执行

负责实现需求的开发者（含 Codex）同时负责设计用例、执行测试和报告结果。开发前从已确认的需求中提取验收条件，再按设计中各模块的职责和接口，确定每个条件应在哪里验证。

- **从需求确定预期。** 每条验收条件至少对应一个用例。用例注明需求编号或条款、涉及的模块或接口、前置条件、输入与操作，以及可观察的预期结果。例如，上传后下载原件，应逐字节比对输入文件与下载内容。
- **按模块边界选择测试层。** 单个模块内的业务规则用单元测试验证；数据或状态跨越模块时，用接口或集成测试验证交接双方的约定；需要多个模块协作才能完成的关键用户流程，再从实际入口做端到端验证。优先复用已有用例。
- **覆盖有意义的边界和失败。** 除正常流程外，针对本次需求涉及的输入边界、依赖失败、重试或恢复行为设计用例。例如，原件已写入对象存储、文件登记却失败时，检查界面是否报告失败，以及重试后数据库是否只有一条有效记录、原件能否下载。
- **用实测结果完成验收。** 执行本次需求的用例和受影响模块的回归用例。失败时保留复现条件，修复后重跑。交付说明列出验证范围、复现命令或手工步骤、实际结果；未执行的场景注明原因。

## 需求完成后的 README 维护

检查仓库根目录的 `README.md`。如果需求改变了用户可用的功能、安装或启动步骤、配置项、使用方法或已知限制，在同一次改动中更新相关说明。README 中的命令和配置示例应与当前实现相符，示例值使用占位符。

## 开发问题与性能优化记录

开发中遇到问题时，由负责实现的开发者在[开发问题与性能优化记录](../knowledge-base/development-notes.md)中说明背景、问题表现及影响。解决后在同一条记录补上采用的方案和验证结果，供后续整理项目亮点。涉及性能优化时，写明原有瓶颈、定位依据和具体改法。有实测数据时，注明测试条件、指标及优化前后的数值；尚未测量时，注明待测。

## GitHub 发布安全检查

每个需求开发完成后，检查本次拟上传的变更。范围包括待推送提交、已暂存和未暂存的改动，以及准备纳入版本控制的新文件。检查代码、配置、测试数据、文档和附件中是否有以下问题。

- 真实的 API 密钥、令牌、密码、私钥、会话凭据或含凭据的连接字符串。
- 个人信息、内部地址、真实日志或数据导出，以及受分享权限限制的课程资料。
- 可能误上传的本地配置、调试输出和数据库文件，或会暴露数据的默认配置和访问权限。

在交付说明中写明检查范围和结果。有问题时，在推送前提示文件位置、风险和建议处理方式。引用问题时使用脱敏描述。如果检查通过，说明在已检查范围内未发现问题。如果有文件无法检查，指出未覆盖的内容。
