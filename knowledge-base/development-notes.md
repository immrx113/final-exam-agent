## 2026-11-28 · R3 复合题的部分漏配

旧 Agent 一旦在整题中找到一个考点，就不再复核余下的要求。订单样例只得到主键 1 题，待核对为零。R3 保存每项要求的原句、位置、已命中与候选，按整题汇总已确认考点。在自建课试用时还发现，以“引用”开头解释外键的讲义定义会被通用提取器过滤；补入定义线索后，两类课程均能从这份材料选择外键。

修正发布从基版读取题目和教学依据，在一个事务内写入去重命中、快照及修正记录。测试在快照写入后人为触发最后一次更新失败，验证整个事务回滚。断开浏览器的首次成功响应后重发，仍只有一个子版本。重启后原版的 Markdown 与原文可逐字核对，隐藏后恢复的考点带回原笔记与勾选。[验收与评测](r3-topic-corrections.md)

## 2026-11-28 · R2 使用 RocketMQ 和 Redisson 恢复后台分析

- 改造前，一次 HTTP 请求要等 Python 完成分析和 MySQL 发布才返回。浏览器在此期间断线，学生无法判断应当重试还是查看新版本。现在服务端在一个 MySQL 事务内登记请求标识、固定输入和待发送状态，随即返回任务号。学生可继续使用上次发布的结果，重发同一请求可找回原任务。
- **RocketMQ 负责投递。** 后台把任务 ID 发给 Broker，Broker 离线时待发送记录留在 MySQL，恢复后自动补投。消费者在发布事务提交后才确认消息。若在这两步之间退出，新消费者收到重投消息时先查任务终态，直接确认已发布的任务。
- **Redisson 协调执行，MySQL 校验发布资格。** 消费者按任务 ID 获取有期限的锁，领取任务时写入本次执行令牌。锁失效后另一个消费者可以接管。发布事务必须匹配当前令牌和有效期，版本表还对任务 ID 设置唯一约束，迟到的执行者无法覆盖接管者的结果。
- 工作台提交时保存 R1 解析产物 ID。消费时按该 ID 读取正文和页码，升级前缺少 ID 的批次在受理时保存片段与历史链接。联调中发现 Spring 代理对象上的字段不能直接读取，改由导入服务的方法读取绑定。等待期间重新识别、服务重启和旧库迁移分别使用独立试用库验证。
- 首次启动容器时，Docker 空卷归属导致 Broker 无法创建存储锁。Compose 用一次性容器设置专用消息卷目录的归属，Broker 继续以镜像内的普通用户运行，启动脚本等待 Broker 监听端口就绪。

在本机独立试用库中，使用真实 RocketMQ、Redis 和 MySQL 注入故障，按任务号核对执行次数和发布版本行数。

| 场景 | 实测结果 |
| --- | --- |
| 发布已提交、消息尚未确认时终止 Java | 重启后捕获同一消息重投，任务共执行 1 次、发布 1 个版本。 |
| 暂停原消费者，断开 Redis，第二个消费者接管后再放行原消费者 | 任务共执行 2 次、发布 1 个版本，原消费者返回后版本号保持一致。 |
| 领取前 Redis 离线；另行注入无效出处及持续超时 | 等待 Redis 恢复期间执行次数为 0。无效出处执行 1 次后失败，持续超时执行 3 次后失败，两项故障均新增 0 个版本。 |

本轮验证了提交可以在分析完成前返回，以及故障恢复后的发布次数。提交延迟的前后对照、分析总耗时和并发吞吐量尚未测量。[复现步骤与逐项验收记录](async-analysis-design.md)

## 2026-11-26 · 前端重构中装饰加号影响文件选择标签精确匹配

- **背景与问题**：在 Task 1（`dual-track-workspace`）实现三栏上传卡与单行快捷导入条时，在 `<label className="picker">` 内增加了 `<span aria-hidden="true">+</span>` 以呈现 `+ 选择课件`。Playwright 的 `getByLabel("选择课件", { exact: true })` 基于关联 `<label>` 的 DOM 文本匹配，读取到 `"+选择课件"`，导致既有导入用例的精确标签定位匹配到 0 个元素。
- **解决方案**：移除含字符文本的装饰 `<span>`，改用不含任何文本节点的矢量 `<svg aria-hidden="true">` 绘制加号图标，并保证同一时刻 DOM 仅渲染展开态或收缩态中的唯一一组 `<label>`。
- **验证结果**：重新执行 `npm.cmd run build --prefix web` 并在无头 Edge 下验证首次引导三栏展开态与已发布单行快捷导入态，`getByLabel("选择课件" | "选择资料" | "选择试卷", { exact: true })` 均唯一命中 1 个控件，视觉加号图标正常显示。

## 2026-11-26 · 四页签与参考计划原地展开下的严格定位器隔离

- **验证结果**：运行 `m2-tests/visibility.mjs` 及无头 Edge 验证脚本，确认计划步骤默认态下 `plan.first().locator("a")` 唯一匹配前置链接、展开态下支持页内对照与 `Esc` 归还焦点、跨页签切换不丢草稿与冲突核对状态。

## 2026-11-26 · 单课程架构局限排查与多课程轻量自举方案选型

- **背景与问题**：完成 M5 与前端重构后，系统虽然在文档解析（PDFBox / LibreOffice / MinerU / Windows OCR）、MinIO 内容寻址、Redis 版本缓存、先修拓扑排序（`StudyPlan`）与视频热度排序（`VideoRules`）上已具备课程无关性，但整体仍只能学习《数据库原理》一门课。全栈排查定位出两层耦合：（1）**工程单例耦合**：MySQL 7 张业务表均无 `courses` 主表与 `course_id` 隔离列，Controller 固定挂载 `/api/course`，`topicId` 命名空间、Markdown 导出标题/文件名、`VideoSource` 搜索词与前端顶栏均硬编码为 `"数据库原理"`，若两门课同时包含同名考点（如《数据库原理》与《操作系统》均考“死锁”），笔记与频次会发生碰撞；（2）**学科词表强耦合**：Python 分析器（`m2/agent.py` + `m2/concepts.py`）依赖约 90 个数据库专有词（`KNOWN` / `CORE`）、范式/主外码同义词 `ALIASES` 及偏数据库的 38 个词尾后缀 `DOMAIN_NOUN`；若直接用于其他课程，不仅数据库 `CORE` 词汇会污染新课程试卷的“待归类”统计，而且失去 `KNOWN` 后，普通冒号定义、不含数据库后缀的 PPT 小标题（如 `信号量`、`B+树`、`LRU`）以及“已知术语行首陈述 / 独立标题兜底”两条路径会大面积失效。
- **解决方案**：在对比“多实例容器隔离”“单实例多课 + 本地/云端 LLM 抽取”“单实例多课 + 纯本地轻量两趟自举抽取”三种方案后，选定**单实例多课程工作台 + Python 轻量两趟扫描自举（Two-Pass Bootstrapping）**方案，兼顾零外部大模型依赖、毫秒级确定性响应与存量 100% 兼容：（1）数据库新增 `V5__courses.sql` 建立 `courses` 表并写入默认种子课（`id='default'`，`topic_ns='数据库原理'`，`profile='database'`），保证历史 `study_states` 的知识点 UUID 逐字节兼容，新建课程使用课程 UUID 作为 `topic_ns` 彻底隔离同名考点；（2）Spring Boot 采用 `@RequestMapping({"/api/course", "/api/courses/{course}"})` 双路径映射与资源归属校验，既支持多课程切换与越权防护，又使既有 M1～M5 测试脚本零破坏复用；（3）Python 侧按 `profile` 分流，`database` 模式原样保留数据库词包，`general` 模式移除数据库 `CORE` 注入，利用本课教材/PPT 自身的标题层级（`###`）、加粗强调、显式定义左值与中英括号对照（如 `最近最少使用算法（LRU）`）执行第 1 趟扫描自举构建本课专属 `DYNAMIC_KNOWN` 与 `DYNAMIC_ALIASES`，配合通用学术中心词后缀、PPT 标题下要点列表聚合、试卷“名词解释”大题上下文感知及已有的通用中文向量模型 `bge-small-zh-v1.5` 完成第 2 趟知识点提取与真题关联。纯符号公式计算课（如高数、线代）的隐含定理判题明确列为当前轻量方案边界。
### 2026-11-27 实测

- **存量与空库。** MySQL 8.4 的独立试用库从 V4 升至 V5，Flyway 报告迁移用时 0.314 秒。默认课升级前后均为 41 个文件、24 个批次、55 个版本、3 条学习记录，按考点、修订号、勾选值和笔记计算的聚合校验和一致。另一空库依次执行 V1～V5 用时 0.401 秒。
- **提取规则。** MinerU 的列表块会输出为无项目符号的逐行文本，通用提取器在同页标题下聚合要点，保留页位置。大题编号用于区分不同题型下相同的小题编号，两字名词如“死锁”在名词解释中可以单独成题。中文操作系统样例的三个人工标注考题关联全部命中，无额外关联；网络样例覆盖 TCP/IP、B+树、缩写边界及噪声过滤。
- **耗时。** Windows 本机、关闭语义、预热后连续运行同一批 200 次。输入为一页操作系统讲义和一份两题的名词解释，输出 2 个考点及 2 个题目。纯 Python 分析耗时中位数 0.093 ms，P95 为 0.129 ms。单独用 tracemalloc 采样的一批峰值分配约 5.5 KiB；该指标仅计 Python 跟踪的分配。此测量不含 OCR、进程启动或 BGE 推理。
- **规则回归。** 启用本机 BGE 后，数据库原有 8 项与新增通用课程 4 项用例全部通过。关闭语义时通过全部规则用例，各跳过 1 项语义专项。规则与语义两种配置下，M2 独立卷均命中 4/5 个关联、零误配，M5 均为查准 4/4、召回 4/6，2/5 题待核对。
- **浏览器与服务。** 两个 MySQL 试用库分别验证旧数据和新课程。双课 Edge 脚本通过 prepare 与真实重启后的 verify。M1 的 11 文件原件字节、OCR 与页码通过；M2 浏览器、展示规则及 502/504 注入通过；M3 笔记冲突、导出、重启和失败恢复通过；M4 固定源的重试及迟到结果隔离通过。真实关键词返回 HTTP 412，BV 目录成功打开第 8 个分 P。M5 自制混合课程、恢复与 UI-01～UI-05 通过。复用已有试用批次时，两次 M5 导入就绪/分析分别为 620/278 ms 和 228/221 ms。M1 PDF/OCR、页文本与 MinerU 契约及 M3/M4 Java 规则测试均通过。

## 2026-11-27 · 课程切换浮层交互命中、Esc 捕获分层与已发布态瞬时闪烁修复

- **背景与问题**：在升级右上角一体化课程切换浮层（`CourseSwitcher.tsx`）、自建课程悬停重命名/删除与跨课草稿暂存时，端到端回归暴露出三处交互与时序边界：（1）课程行右侧的「重命名」「删除」按钮若同时设置 `opacity: 0; pointer-events: none` 并仅在 `:hover` 恢复 `pointer-events: auto`，Playwright 指针命中检测及支持触控+触控板的混合设备直接点击按钮坐标时会被父级 `<li class="course-menu-item">` 拦截；（2）当右侧「页内原文对照」抽屉（`EvidenceDrawer`）与顶栏课程浮层同时打开时，按 `Escape` 若走常规冒泡阶段会同时触发 `window` 上的抽屉关闭监听，误关正在阅读的原文面板；（3）已发布课程初次加载或切回重挂载期间，`publishedSnapshot` 异步请求尚未返回前的十余毫秒内 `Boolean(publishedSnapshot)` 为 `false`，导致导入区短暂渲染三栏展开卡再跳变为单行快捷导入条，若在该窗口期内立即向 `<input type="file">` 注入文件会因控件卸载重挂载丢失首份草稿。
- **解决方案**：（1）移除 `.course-row-actions` 上的 `pointer-events: none`，常态仅通过 `opacity: 0` 保持视觉极简，悬停、`:focus-within` 与 `hover: none` 触屏下显式浮现，兼顾干净视觉与直接点击可达；（2）`CourseSwitcher` 打开期间在 `window` 捕获阶段（`useCapture = true`）监听 `Escape` 并调用 `stopImmediatePropagation()`，仅关闭顶层课程浮层并将焦点归还触发胶囊，保护底层 `EvidenceDrawer` 不受影响；（3）在 `Workspace` 中结合列表接口已知的 `course.hasPublished`（`Boolean(publishedSnapshot) || (initialLoading && course.hasPublished)`）决定导入栏初始展开态，并在快照读取或新发布后同步更新 `courses` 状态，彻底消除已发布课程挂载时的布局跳变与文件输入竞态。
- **验证结果**：在独立试用环境运行 `CourseRulesTest`、`ui-refactor.mjs`、`m2-tests/visibility.mjs`、`m6-tests/multi-course.mjs`（`prepare` + 真实重启 Java + `verify`，覆盖 Esc 双层叠加、草稿恢复、悬停改名、二次确认删除及 390px/1280px 视口检测）以及 `m2-tests/browser.mjs`、`m2-tests/edges.mjs`、`m3-tests/course.mjs` 全部一次通过。

## 条目模板

- **日期与模块**：问题发生在哪个阶段、哪个功能或模块？
- **背景与问题**：当时要完成什么任务？在什么条件下出现了什么现象，影响了谁或哪一步操作？
- **解决方案**：如何定位原因，最终改了什么，为什么这样改？仍在排查时先写当前进展。
- **验证结果**：如何复现并确认修复有效？可附对应的仓库代码、测试用例或提交。
- **性能优化（如涉及）**：原先慢在哪里或消耗了什么资源？用什么证据定位瓶颈，采取了什么优化？记录相同测试条件下的指标、单位和优化前后数值，尚未测量时注明待测。
