# M1 测试用例

> 依据 `m1-acceptance.md` 的 M1-01～M1-09 生成，供 codex 开发 M1 时作为可执行验收依据。只以上述 9 条产品行为作为判断依据，不涉及知识点、频次、笔记、导出和视频（M2 起另行验收）。每条用例列出需求编号、优先级、前置条件、输入、步骤、逐步可观察结果与适合的验证层；需要故障注入的用例在「故障注入」字段单独标注；超出给定范围的额外建议归入「探索项」。示例文件均可自制，无需真实课程资料。

## 1. 测试环境与样例约定

- 依赖：MySQL 8.4、MinIO（见 `compose.yaml`）、Spring Boot 后端、React 前端，以及 `architect.md` 所列的 LibreOffice、PDFBox、Tesseract 解析链。
- 样例人工标注见 `m0/fixtures/truth.json`；其 `locations` 中出现的 `lesson.ppt`/`lesson.pptx`（第 2 张「函数依赖」）、`notes.doc`/`notes.docx`（第 2 页「候选键」）、`outline.md`（第 3 行「投影」）、`clear.png`（清晰题干）、`unclear.jpg`（受损题号）可直接沿用。其余样例按需自制。
- 自制样例清单（对应各用例）：

| 样例文件 | 内容约定 | 用途 |
| --- | --- | --- |
| `db-courseware-1.pdf` | 两页文本 PDF，第 2 页含文本片段 | 课件/文本定位 |
| `db-material.pdf` | 文本 PDF | 资料 |
| `db-exam.pdf`、`db-exam-2.pdf` | 文本 PDF | 试卷（多选） |
| `lesson.ppt`、`lesson.pptx` | 第 2 张写「函数依赖」 | 课件转换预览 |
| `notes.doc`、`notes.docx` | 第 2 页写「候选键」 | 资料 Word 固定预览 |
| `outline.md` | 第 3 行写「投影」，之前有空行作定位干扰 | 资料 Markdown |
| `clear.png`、`unclear.jpg` | 清晰题干 / 受损题号 | 试卷图片 |
| `scan-3p.pdf` | 第 1 页清晰中文、第 2 页受损仅题号、第 3 页关系代数含下标 | 扫描 OCR |
| `corrupt.pdf` | 损坏 PDF（不可解析） | 失败/重试 |

- 验证层标签含义：
  - **浏览器**：React 界面的端到端交互（建议 Playwright）。
  - **接口**：Spring Boot HTTP 业务 API（`/api/v1/...`）集成测试。
  - **存储集成**：MySQL 与 MinIO 的实际读写、事务与持久化断言。

## 2. 测试用例

### TC-M1-01-1 三个上传区、多选与提交前改区

- **需求编号**：M1-01
- **优先级**：P0
- **前置条件**：已新建《数据库原理》课程；后端与存储就绪。
- **输入**：课件区 `db-courseware-1.pdf`；资料区 `db-material.pdf`；试卷区 `db-exam.pdf` 与 `db-exam-2.pdf`（一区多选）；提交前把 `db-exam-2.pdf` 从试卷区改到资料区。
- **步骤**：
  1. 打开课程上传页，在「课件」区选择 `db-courseware-1.pdf`。
  2. 在「资料」区选择 `db-material.pdf`。
  3. 在「试卷」区一次选择 `db-exam.pdf` 和 `db-exam-2.pdf`。
  4. 观察三个区域各自列出的文件名。
  5. 提交前把 `db-exam-2.pdf` 从「试卷」区移动到「资料」区。
  6. 提交。
- **逐步可观察结果**：
  1. 「课件」区仅列出 `db-courseware-1.pdf`，文件名正确。
  2. 「资料」区仅列出 `db-material.pdf`。
  3. 「试卷」区同时列出 `db-exam.pdf` 与 `db-exam-2.pdf`。
  4. 三个区互不混淆；同为 `pdf` 扩展名的文件在不同区分别显示，互不串区。
  5. `db-exam-2.pdf` 在「资料」区出现、从「试卷」区消失。
  6. 提交后用途与最后一次选择一致：`db-courseware-1.pdf`→`courseware`，`db-material.pdf`、`db-exam-2.pdf`→`material`，`db-exam.pdf`→`exam`；同一 `pdf` 扩展名分别承担课件/资料/试卷三种用途。
- **验证层**：浏览器（各区文件名、多选、改区交互与提交后用途）；接口（`POST /files` 携带 role、`PATCH /files/{file_id}` 修改 role）；存储集成（MySQL file 表的 `role` 列持久化正确）。
- **故障注入**：否。

### TC-M1-01-2 改区只影响下一次提交

- **需求编号**：M1-01
- **优先级**：P1
- **前置条件**：某文件已以 `courseware` 提交，且已存在对应分析任务。
- **输入**：对该文件调用 `PATCH /files/{file_id}` 将 role 改为 `material`。
- **步骤**：
  1. 修改 role。
  2. 查询已提交任务的输入用途。
  3. 以新用途重新提交。
- **逐步可观察结果**：
  1. `PATCH` 返回更新后的 `File`，role 为 `material`。
  2. 已提交任务继续使用提交时的 `courseware`，不被改区影响。
  3. 新提交使用 `material`。
- **验证层**：接口 + 存储集成（任务输入快照与文件当前 role 分离）。
- **故障注入**：否。

### TC-M1-02-1 提交后逐文件状态与刷新恢复

- **需求编号**：M1-02
- **优先级**：P0
- **前置条件**：已上传多个待分析文件。
- **输入**：一批含可成功解析的 PDF 与需转换的 PPT。
- **步骤**：
  1. 提交文件。
  2. 立即观察页面。
  3. 刷新课程页。
  4. 再次观察页面。
- **逐步可观察结果**：
  1. 提交返回任务，页面显示任务已提交。
  2. 各文件依次显示 `queued` → `processing` → `ready` 或 `failed` 之一。
  3. 刷新后从 `latest_job_id` 恢复轮询。
  4. 刷新后仍能看到每个文件的排队/处理中/最终结果，已提交任务与结果可找回。
- **验证层**：浏览器（刷新恢复轮询与逐文件状态）；接口（`POST /analyses` 返回 202 与 `job_id`，`GET /analyses/{job_id}` 返回 `Job` 及 `files[].status`）。
- **故障注入**：否。

### TC-M1-03-1 文本 PDF 定位与原件下载（首条端到端用例）

- **需求编号**：M1-03（与 M1-01 组合为端到端首条用例）
- **优先级**：P0
- **前置条件**：已完成一次包含两页文本 PDF 的导入，处理完成。
- **输入**：两页文本 PDF，第 2 页含文本片段。
- **步骤**：
  1. 上传并完成处理。

### TC-M1-06-1 扫描 PDF 逐页 OCR 与存疑核对

- **需求编号**：M1-06
- **优先级**：P1
- **前置条件**：OCR 环境可用；`scan-3p.pdf` 已上传并完成处理。
- **输入**：`scan-3p.pdf`——第 1 页清晰中文、第 2 页受损仅能辨认题号、第 3 页关系代数公式含下标。
- **步骤**：
  1. 上传并完成处理。
  2. 观察第 2 页的结果。
  3. 点击第 3 页关系代数片段。
- **逐步可观察结果**：
  1. 第 1 页逐页 OCR 得到可读中文。
  2. 第 2 页显示待核对提示（如 `UNCERTAIN_OCR`），不误报为成功；可见题号但仍标存疑。
  3. 第 3 页可点回原页核对下标（`page_basis=original`）。
  4. 按样例核对定位即可，不规定通用 OCR 准确率。
- **验证层**：浏览器（待核对提示、点回原页）；接口（`Job.files[].issues` 含 `locator`，`Source.locator.page_basis` 为 `original`）；存储集成。
- **故障注入**：否（受损页为输入数据，非运行时注入）。

### TC-M1-07-1 有效文件与损坏文件共存、失败原因与原件下载、重试

- **需求编号**：M1-07
- **优先级**：P0
- **前置条件**：准备一个有效 PDF 和一个损坏 PDF。
- **输入**：`db-courseware-1.pdf`（有效）+ `corrupt.pdf`（损坏）。
- **步骤**：
  1. 同时提交两者。
  2. 观察逐文件结果。
  3. 下载坏文件原件。
  4. 修复临时故障后重试坏文件。
- **逐步可观察结果**：
  1. 有效文件进入处理并可核对（`ready`）。
  2. 坏文件显示失败原因（如 `PARSE_FAILED`），任务状态为 `partial`，不误报成功。
  3. 已收存的原件仍可下载。
  4. 修复后可单独重试坏文件，有效文件不受影响。
- **验证层**：浏览器（失败原因展示、重试入口）；接口（`Job.files[].status`/`issues`、`POST /analyses/{job_id}/retry`）；存储集成（坏文件原件仍可读）。
- **故障注入**：是（第 4 步需注入并解除一次临时故障——模拟转换/解析失败后恢复——再单独重试）。

### TC-M1-08-1 写原件时中断 MinIO

- **需求编号**：M1-08
- **优先级**：P0
- **前置条件**：准备一个可上传文件。
- **输入**：一个 PDF。
- **步骤**：
  1. 在写原件到 MinIO 时注入故障（停止/断开 MinIO）。
  2. 观察提交结果。
  3. 恢复 MinIO 后重传同一文件。
- **逐步可观察结果**：
  1. 失败不会显示成导入成功（返回 `STORAGE_UNAVAILABLE` 或失败状态）。
  2. 恢复后重试最终只有一条有效文件记录，原件可打开。
  3. 重复请求不产生重复条目。
- **验证层**：接口（503/失败状态）+ 存储集成（MySQL 记录数、MinIO 对象、内容摘要寻址的幂等）。
- **故障注入**：是。

## 3. 探索项（超出给定验收范围，非强制）

以下为额外建议，供 codex 在实现可靠性与边界时参考，不作为 M1 验收判据：

- 上传超过大小上限的文件，核对 `413 FILE_TOO_LARGE` 的提示与其余文件可继续上传。
- 上传不支持格式（如 `.zip`/`.exe`），核对 `415 UNSUPPORTED_FORMAT` 的提示与隔离。
- 同名不同内容的文件：确认按内容摘要寻址，不被文件名误判为重复。
- 空文件（0 字节）与超大文件的处理与轮询体验。
- 同一课程并发提交两个不同清单时返回 `409 JOB_ACTIVE` 的行为。
- 预览尚在生成时打开片段（`409 PREVIEW_PENDING`）的降级与原件回退。
- 同卷多张图片的 `paper_group`/`page_order` 登记（虽属 M2 统计，但 M1 已写入 file 元数据）。
- 慢转换/慢 OCR 下前端轮询超时与取消的体验。
- 网络中断时前端重试与错误提示。
- 真实受损页上 OCR 的耗时与内存表现（为 M5 本机试用积累基线）。
