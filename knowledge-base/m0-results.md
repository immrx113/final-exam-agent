# M0 可行性验证实测记录

2026-11-24，在一台 Windows 电脑上，用自制《数据库原理》材料跑通了 Java 读取扫描 PDF、中文 OCR、Python 模型匹配和回看原页。建议 M1 沿用已测的 Office 转 PDF 和原页渲染路径。对公式页始终提供原页入口，OCR 文本只供检索和辅助阅读。

## 输入与结果

| 输入 | 人工标注 | 本机结果 |
| --- | --- | --- |
| 三页纯图像 PDF，第 1 页 | 第 1 题，候选键 | 从“唯一标识元组的最小属性集合”匹配到候选键，可回看第 1 页。 |
| 同卷第 2 页 | 第 2 题，题干受损，应待核对 | OCR 仅保留题号，Agent 返回空考点和待核对原因，可打开该页图像。 |
| 同卷第 3 页 | 第 3 题，关系代数，含投影符号和下标 | 考点正确。原图中的 πₓ(R) 被识别成 T1x(R)，模型仍给出关联。当前规则不能自动发现这种局部公式错误。 |
| PPT、PPTX 各一份 | 第 2 张讲“函数依赖” | 两份实物均经 LibreOffice 转为 PDF，PDFBox 在第 2 页读到预期文字。 |
| DOC、DOCX 各一份 | 第 2 页讲“候选键” | 两份固定版预览均在第 2 页读到预期文字。复杂排版的重排率还需要真实文件测量。 |
| Markdown | 第 3 行讲“投影” | 逐行读取，预览链接指向第 3 行。 |
| PNG、JPEG | 清晰题干、受损题号 | 分别从原图识别到预期内容，可打开独立图像。 |

3 个题号全部吻合，2 个可判定考点均命中，1 个预期弃判。此样例上没有考点漏配或误配，发现 1 处明确的公式转写错误。每页只有一题，每道可判题只有一个目标考点。多题切分、多考点匹配、生成新知识点和真实班级试卷上的准确率仍待验证。

## 模型、调用和测量口径

- Windows build 26100，AMD Ryzen 9 7845HX，24 个逻辑处理器，系统可用物理内存总量 15.22 GiB。Java 21.0.10，Python 3.12.14，LibreOffice 26.8.3.1，PDFBox 3.0.5，Gson 2.11.0。光栅化使用 144 DPI，识别使用 Windows 简体中文 OCR。
- 选用 BGE-small-zh-v1.5 量化 ONNX 中文向量模型，从人工给定的 3 个候选中匹配考点。ONNX Runtime 1.32.0 使用 CPU、4 个推理线程，tokenizers 0.23.3。模型文件 24,010,842 字节，准备脚本固定了模型和分词器的 SHA-256。该配置只验证候选匹配，生成式模型的速度和质量仍需独立测试。
- 最终一批 3 页，Agent 内部计时 95 ms，其中模型前向计算与匹配约 12 ms。Python 进程峰值工作集 102.0 MiB。95 ms 包含模型加载、分词和匹配，不含 Python 启动、库导入、Java、Office 转换和 OCR。单次读数只用于这台机器和该批次。
- 原型通过标准输入输出传递 UTF-8 JSON。Java 核对版本、批次、证据片段和候选 ID，并拒绝缺失或重复片段。保存的样例可重放。模型收到 OCR 文字及候选定义，题目答案单独用于验收。此契约仅适用于 M0 的进程调用。[实际请求](../m0/examples/request.json) · [实际响应](../m0/examples/response.json) · [逐项验收](../m0/examples/evaluation.json)
